## Направление

Проект эволюционирует из просмотрщика с возможностью генерации в **ИИ-студию персонажей с их соцсетями**: создал персону → выбрал её в редакторе при генерации → изображения копятся в её авто-альбоме → набрал набор для поста → ИИ написал текст под легенду персонажа → опубликовал в Instagram/Telegram/VK → всё оседает в истории персоны.

## Цели (порядок важности)

1. **Цель 1 — Telegram (сейчас).** Авторизация в Telegram и публикация работ **от имени пользователя** (личного аккаунта, НЕ бота): отправка контакту из списка, в «Избранное» (Saved Messages), публикация в свою группу/канал.
2. **Цель 2 — ВКонтакте (потом).** Авторизация через браузер с автоматическим открытием, перехват токена после входа и вставка его в приложение. Публикация фото/видео на стену — свою и групп, где пользователь администратор. Личные сообщения **не поддерживаются**: право `messages` новым приложениям через Implicit Flow не выдаётся (dev.vk.com).
3. **Цель 3 — Instagram.** Публикация фото/видео/карусели от **личного** аккаунта через Private API (instagrapi). Официальный Graph API не умеет постить за личный аккаунт.
4. **Цель 4 — AI-постмейкер.** Легенда персонажа + описания выбранных работ → текст поста в стиле персонажа и под формат конкретной соцсети. Использует существующий AI-слой (PromptTask / InstructionBundle / ExecutionRouter), отдельный пайплайн не нужен.
5. **Цель 5 — Персоны и альбомы.** Отдельная страница персон (CRUD, история изображений, история публикаций), линковка генерируемых изображений к персоне в редакторе, авто-альбом персонажа в библиотеке.

## Общие принципы

- **Полностью локально, без деплоя.** Никакого webhook-сервера, хостинга или публичного URL. Все вызовы — исходящие HTTPS-запросы к API Telegram/VK с локальной машины.
- **Авторизация — отдельной кнопкой**, по образцу карточек CLI-интеграций в `ai_settings.html` / `ai-settings.js` (`/api/ai/cli-integrations`).
- **Секреты шифруются** так, чтобы другой локальный пользователь Windows не мог их вытащить из файлов приложения.
- Экспортируются **image/video** (работы из медиатеки), не воркфлоу.
- **Публикация — только ручная, по кнопке** (жёсткое ограничение для личных аккаунтов Telegram/Instagram): каждый publish = один явный клик пользователя, без шедулинга, батчей, авто-повторов и массовых рассылок. Свой аккаунт, локальный IP, низкий объём.
- **Не обходим лимиты провайдеров.** Сервисы сами ограничивают rate limits — это штатный механизм, а не препятствие. Бан реален только при попытке **обойти** аккаунтные лимиты (массовость, автоматизация в обход API, смена идентичности). Поэтому встроенные лимиты соблюдаем как контракт, а не обходим; тогда риск блокировки минимален.

## Публикация: общий контракт

Единая сигнатура для всех трёх транспортов — модалка публикации и роут не знают деталей провайдера:

```
POST /api/social/publish
{
  "provider": "telegram" | "vk" | "instagram",
  "target": { "type": "contact" | "saved" | "group" | "wall" | "group_wall" | "feed", "id"?: string, "title"?: string },
  "assets": [{ "asset_id": string, "kind": "image" | "video" }],
  "text": string | null
}
```

- **`target`** — абстракция места назначения; каждая соцсеть мапит её на свой тип:
  - telegram: `contact` / `saved` / `group` → `chat_id`;
  - vk: `wall` (своя) / `group_wall` → `owner_id` (+ `from_group=1` для групп);
  - instagram: `feed` → `photo_upload` / `video_upload` / `album_upload`.
- **`assets`** — работы из медиатеки (локальные оригиналы). Telegram/VK — до 10 медиа (album / вложения), Instagram-карусель — до 10.
- **`text`** — черновик из постмейкера или введённый вручную; провайдер решает, как оформить (caption / message / post + хештеги).

### Модель ошибок и частичные сбои

```
{
  "status": "ok" | "partial" | "failed",
  "provider": "...",
  "target": { ... },
  "published": [asset_id, ...],
  "failed": [{ "asset_id": string, "reason": string }],
  "external_url"?: string,
  "error"?: string
}
```

- `partial` — часть медиа ушла (например, 2 из 3 вложений), остальное — в `failed`. Пользователю показываем, что ушло, что нет, и даём «повторить только failed».
- `failed` — публикация не прошла целиком; `error` — человекочитаемая причина.
- Каждый publish — изолированная операция: сбой одного провайдера не влияет на остальные; результат всегда сохраняется в `publications`.
- Повторы — только по явной кнопке пользователя (см. «Общие принципы»); внутри одного клика никаких авто-ретраев.
- Rate limits провайдеров возвращаются как ошибки с понятным текстом («слишком много запросов, подождите N»), без попыток их обойти.

## Цель 1: Telegram

### Почему не Bot API
Bot API (`t.me/BotFather` + токен бота) позволяет действовать только **от имени бота**. Пользователю нужна публикация от своего аккаунта → Bot API не подходит.

### Подход: MTProto (Telethon)
Для работы от имени личного аккаунта используется **MTProto-клиент**:

- Библиотека: **Telethon** (`pip install telethon`; версия **1.44.0**, совместима с Python 3.12 — венв 3.12.5). В `pyproject.toml` пока нет — добавить `telethon = "^1.44"`.
- Нужен `api_id` + `api_hash` — выдаются один раз на `my.telegram.org` под аккаунтом пользователя (локальная регистрация «приложения», без деплоя).
- Авторизация интерактивная, двумя способами:
  - **QR-код** (в консоли/в web-странице) → скан в мобильном приложении Telegram (удобно, если телефон уже авторизован);
  - **номер телефона + код** (код приходит в Telegram/SMS) + при необходимости пароль 2FA.
- После успешного входа Telethon сохраняет **сессию** (файл или строку), которую можно использовать повторно без повторной авторизации.

### Локальное приложение Telegram (tdata) — не переиспользуется
Сессия Telegram Desktop хранится в `tdata` в зашифрованном виде и привязана к конкретной сборке приложения; сторонние библиотеки её официально не читают. Поэтому авторизация делается через MTProto-поток (QR или телефон+код), а не через чтение tdata.

### Хранение и шифрование
- **`api_id` / `api_hash`** — не секреты уровня пароля, но храним в ConfigStore.
- **Сессия Telethon** (это и есть «токен» доступа к аккаунту) — шифруется:
  - Телефон / StringSession — сохранять в Windows Credential Manager через `keyring` (см. `app/ai/secrets.py`: `SERVICE_NAME = "comfyui-meta-viewer"`, паттерн `SystemSecretStore.get/set/delete`). `keyring` уже в зависимостях (`^25.7`), на Windows бэкенд — DPAPI/Windows Credential Manager.
  - Либо файл сессии Telethon с паролем/в каталог с ограниченными правами.
- Итоговое требование: секрет читается только тем же Windows-пользователем; в репозиторий/конфиги-json не попадает.

### Таргетинг и отправка
- «Отправить контакту из списка» → получаем контакты/диалоги (`client.get_dialogs()`, поиск по имени), выбираем `chat_id`.
- «Добавить в избранное» → Saved Messages = диалог с самим собой (`me`).
- «Опубликовать в свою группу» → `client.send_file(chat, file=..., caption=...)`; медиа с диска (оригиналы лежат локально).
- Несколько работ → `album` (группа медиа).
- Публикация — только по явной кнопке пользователя (см. «Общие принципы»); никаких фоновых рассылок.

### Реализационные детали (по ресёрчу Telethon 1.44.0, 2026-08)
- Крипто: по умолчанию `pyaes` (чистый Python, медленно); опционально `cryptg` (C-скорость, есть win_amd64-колёса для CPython 3.11–3.14; венв 3.12 — ок).
- Gotcha с v1.31: `imghdr` удалён — при отправке фото из BytesIO обязательно задавать `photo.name = 'x.jpg'`.
- Альбом: `send_file` со списком файлов сам разбивает на альбомы чанками по 10 (`SendMultiMediaRequest`); `caption` можно передать списком (попарно с файлами).
- Rate limits: `FloodWaitError(420)` несёт `.seconds` — показываем «слишком много запросов, подождите N»; `flood_sleep_threshold` по умолчанию 60с. Не обходим (см. «Общие принципы»); при `PeerFloodError` аккаунт ограничен — останавливаемся.

## Цель 2: ВКонтакте (потом)

### Результат ресёрча (2026-08): user-токен личной стены для новых приложений недоступен
- **Блокер подтверждён ресёрчем, а не только слухами:** права `wall`/`photos`/`video` для user-токенов новым приложениям **не выдаются** — dev.vk.com пишет «выдаётся в исключительных случаях через запрос в поддержку», а ответы поддержки (февраль–март 2026) систематически отказывают со ссылкой на оферту п.7.2 («расширенные API-доступы больше не выдаются»).
- Легаси Implicit Flow (`oauth.vk.com/authorize?...response_type=token`) для новых приложений **деприкейтнут**: новые приложения идут через VK ID (`id.vk.com`) OAuth2+PKCE, который не выдаёт scopes API-методов (только `vkid.*`, email, phone).
- Старые Standalone-приложения (до ~марта 2025) всё ещё работают: Implicit Flow с `redirect_uri=https://oauth.vk.com/blank.html` (другой redirect_uri → `invalid_scope`), но их токены **привязаны к IP**.
- Вывод (D-010): **основной путь VK-транспорта — публикация в свою группу community-токеном** (официально поддерживается, особых прав не требует). Публикация на **личную стену** — только если у пользователя есть старое приложение с выданным scope `wall`, либо через документированный workaround (генератор токенов `vkhost.github.io` — неофициальный, токены привязаны к IP); для продукта это не дефолт.

### Токен
- **Основной путь (группа):** community-токен с правами сообщества (`photos`, `video`, `wall`, `offline`). Получение: в настройках сообщества → Работа с API → Ключи доступа; в приложение вводится вручную (copy-paste из кабинета VK). `client_id`/`group_id` в ConfigStore + поля в UI.
- **Личная стена (опционально):** user-токен со scope `photos,video,wall,offline` — только при наличии приложения с выданным scope (старое приложение до ~марта 2025 / редкий положительный ответ поддержки). Без него личная стена недоступна.
- **Личка недоступна:** право `messages` новым приложениям не выдаётся (`messages.send` не сработает). В ЛС не публикуем.
- Ограничения: `wall.post` — до 10 вложений, пост обязан содержать текст/фото/видео/сниппет/статью (с 2025-08-27); дневной лимит личной стены неофициальный и противоречивый (25/40/50), сообществ ~50/день; `video.save` — 5000 вызовов/день, error 15 при `wallpost=1` без права `wall`.

### Поток авторизации (браузер, без деплоя)
1. **Community-токен (основной путь):** генерируется в кабинете сообщества и вводится в поле настроек приложения; валидация `groups.getById` → шифрование в keyring (`social:vk`).
2. **User-токен (только при наличии приложения со scope `wall`):** кнопка «Авторизоваться в ВК» открывает `https://oauth.vk.com/authorize?client_id=<id>&scope=photos,video,wall,offline&redirect_uri=https://oauth.vk.com/blank.html&response_type=token`.
3. Пользователь входит → VK редиректит на `blank.html#access_token=...&expires_in=...&user_id=...`.
4. **Перехват токена** из URL-фрагмента:
   - приложение поднимает локальный слушатель / через helper-страницу читает фрагмент и передаёт токен в приложение;
   - если перехват нереализуем (например, нестандартный `redirect_uri` ломает методы Standalone-приложения) — **fallback становится основным путём**: подсказка скопировать `access_token` из адресной строки и вставить в поле (D-009).
5. Валидация: `users.get` (user) / `groups.getById` (community) с полученным токеном.
6. **Шифрование токена** — тот же механизм `keyring` (Windows Credential Manager / DPAPI), что и для Telegram-сессии.

### Публикация
- Фото (группа): `photos.getWallUploadServer?group_id=` → загрузка файла → `photos.saveWallPhoto` → attachment `photo{owner}_{id}` → `wall.post` (`owner_id=-<gid>`, `from_group=1`).
- Видео (группа): `video.save` (с `wall=1` и `group_id`) → `upload_url` → PUT видео → `wall.post`.
- Личная стена (если есть user-токен со scope): `photos.getWallUploadServer` (без `group_id`) → `photos.saveWallPhoto` → `wall.post` (`owner_id=<user_id>`).
- Личка не поддерживается (`messages` новым приложениям не выдаётся).

## Цель 3: Instagram

### Почему не официальный Graph API
Instagram Graph API (через Facebook/Meta-приложение) публикует **только** в Business/Creator-аккаунты, требует связку с Facebook Page, app review (право `instagram_content_publish`) и короткоживущие токены. Для «публиковать за личный аккаунт, полностью локально, без деплоя» не подходит — та же логика, что с Telegram (Bot API вместо MTProto).

### Подход: Private API (instagrapi)
- Библиотека: **instagrapi** (`pip install instagrapi`; версия **2.18.12**, в metadata `requires-python >=3.10` — венв 3.12.5 ок; уточнено ресёрчем 2026-08). В `pyproject.toml` пока нет — добавить.
- Авторизация: логин + пароль; при необходимости 2FA (TOTP) и code challenge (код по SMS/email/чекпойнт).
- Сессия: `client.dump_settings()` → JSON-строка; шифровать в keyring (как Telegram StringSession). **Обязательно** `client.load_settings()` перед `login()` (пинит fingerprint устройства — снимает ~9/10 челленджей); сессия только через полный логин — один `sessionid` без сессии ломает загрузку (login_required/500).
- Публикация: `photo_upload(path, caption)`, `video_upload`, `album_upload([...])` (карусель 2–10 шт., фото+видео можно миксовать).
- Фото: JPEG/PNG, соотношение 4:5…1.91:1, пре-резize до 1080×1080 / 1080×1350 q=92; >8MB — ошибка; карусель кропится по соотношению первого фото.
- Лимиты: посты/час и риск challenge при подозрительной активности. Публикация **ручная, по кнопке**, низкий объём — как и в Telegram. Периодическая ломка из-за дрейфа UA/версии приложения (фев 2026: `set_user_agent('Instagram 410.0.0.0.96 …')`, `device_settings.app_version` 416.0.0.47.66, параметр `override_app_version` с 2.6.0) — держим актуальную версию instagrapi.

### Риски
- Private API — неофициальный путь (в отличие от Telegram/VK), поэтому checkpoint/блокировки возможны при подозрительной активности. Но это **не «бан за сам факт»**: сервисы ограничивают rate limits, а не наличие интеграций; блокировка наступает при попытке обойти аккаунтные лимиты или при аномальном поведении (смена IP/UA, массовость, автоматизация в обход лимитов). Соблюдаем лимиты и единый профиль клиента — риск низкий.
- Сессия ломается при смене IP/User-Agent/устройства; храним сессию в keyring и стараемся переиспользовать без повторных логинов, держим один клиент/один IP/один UA.

## Цель 4: AI-постмейкер для персонажей

Идея: в библиотеке выделяем одно или несколько изображений → «Опубликовать» → модалка (соцсеть + таргет) → выбираем персону/легенду → ИИ сочиняет текст поста под характер персонажа и под формат соцсети → пользователь редактирует и публикует.

### Поля персоны: легенда ≠ внешность ≠ примеры
У персоны три независимых текстовых поля, используемых по-разному:

- **Легенда** — биография персонажа (кто он, чем занимается, стиль общения). Для генерации **изображений** не используется. Для генерации **текста постов** это **главный фактор**: легенда инжектится плейсхолдером прямо в системную инструкцию агента как его роль.
- **Внешность** (appearance) — детальное описание внешности персонажа (обычно на английском, в стиле промпта). Влияет **только** на генерацию изображений.
- **Примеры постов** (examples) — голос персонажа в соцсетях, few-shot для текста постов.

Пример (грубый):

```text
Легенда: Анастасия Котельникова, родилась в 1995, занимается художественным балетом и ведёт личный блог в Instagram. Стиль общения лаконичный и милый, старается ярко описать посты и заинтересовать публику, зумерский стиль общения.

Внешность: A young woman with very long, straight platinum blonde hair and front bangs sits on the floor. She has pale, pristine, flawless skin texture with realistic microscopic pores, clean skin tone, zero tattoos, zero moles, and zero skin markings across her entire body.

Примеры постов:
"Ой, мальчики, я сегодня утром проснулась и поняла, что давно вас не радовала 💖 не забывайте ставить лайки 😘".
"Меня сегодня снова бросил очередной мудак... 💔 Вы мои самые любимые и лучшие, хочу чтобы кто-то из вас был моим парнем, а не эти мажорики...".
```

### Персона как слой в InstructionBundle
Персона — это не отдельный «агент, который что-то делает», а **слой в промпт-конструкторе** (компилятор из 06A):

- **Генерация изображений** (`generate` / `reconstruct`): в InstructionBundle подставляется **только `appearance`** — как стабильный блок identity (облик персонажа) поверх family base + operation + scenario. Легенда не участвует.
- **Текст поста** (`social_post`): системная инструкция собирается из двух уровней — **техническая часть из скилла/operation manifest** (как правильно писать посты) + **`legend` плейсхолдером на верхний уровень как роль (биография персонажа)**. `examples` — few-shot примеры стиля. Такая композиция («технический базис + биография поверх») снижает галлюцинации агента и удерживает нужный стиль, а не только имитирует его.
- Поля персоны — пользовательские данные из БД; канонические operation/scenario manifest остаются в `app/ai/prompting/content/`. Компилятор собирает итоговую системную инструкцию: скилл (техника) → плейсхолдер роли с легендой → примеры.

### Как это ложится на существующий AI-слой
Никакого отдельного «магического» пайплайна — персоны и легенды встраиваются в PromptTask / InstructionBundle / ExecutionRouter (см. 06A):

- Новая операция `social_post` в реестре операций: `app/ai/prompting/content/operations/social_post.md` (по образцу `enhance.md`).
- Персона входит в компиляцию как слой (см. выше «Персона как слой в InstructionBundle»): внешность → identity (изображения), легенда → роль (текст постов), примеры → few-shot.
- Выбранные изображения попадают в постмейкер через vision: для **мультимодальных** профилей изображение передаётся напрямую (модель «видит» кадр); для остальных — структурированное описание (`SceneSpec` из операции `reconstruct`). В обоих случаях в манифесте `social_post` — жёсткое правило: не выдумывать детали, которых нет на кадре; результат — редактируемый черновик.
- **Output contract зависит от соцсети** (параметр, не отдельная операция): Instagram — caption + набор хештегов; Telegram — обычное сообщение (без хештегов по умолчанию); VK — пост + опциональные хештеги.
- **Хештеги — политика «персона + контент»:** свои персональные теги с персоны + контентные от темы поста. ИИ предлагает до N (Instagram ~10, VK опционально 3–5, Telegram 0); всё в черновике и редактируется пользователем.
- Выполнение — через существующий ExecutionRouter: direct OpenAI-compatible профиль или agent-host (OpenCode/Claude Code). Обе ветки уже реализованы в `app/ai/`.
- Результат — черновик (`ai_jobs` / `ai_prompt_drafts`), который пользователь **обязательно редактирует перед публикацией**. Авто-публикация без подтверждения не предполагается.

### Хранение
- `personas` — персона: имя, аватар (asset_id), **legend** (биография — роль агента при генерации постов), **appearance** (для генерации изображений), **examples** (few-shot для постов). Все три поля — свободный текст; легенда и примеры участвуют в `social_post`, внешность — в `generate`/`reconstruct`.
- `persona_assets` — связь asset ↔ персона.
- `publications` — история публикаций: провайдер, таргет, текст поста, выбранные assets, статус, внешняя ссылка, ссылка на `ai_job`.

## Цель 5: Персоны, альбомы и история

### Страница персон
Отдельная HTML-страница (`personas.html`), CRUD персонажей. Внутри персоны:
- все привязанные изображения (сетка);
- история создания изображений (по датам/по генерациям);
- история публикаций: какие посты, в какие соцсети, какие изображения были выбраны.

### Линковка в редакторе
В `workflow_editor.html` при генерации — необязательное поле «Персона». Сгенерированные работы автоматически линкуются к персоне (`persona_assets`).

### Авто-альбом
При создании персоны автоматически создаётся виртуальный альбом (по модели 03_MEDIA_LIBRARY_ALBUMS_AND_FAVORITES): «Персона: <имя>». В библиотеке — фильтр по персонам. Разделение «физическое / виртуальное» сохраняется: линковка не копирует и не перемещает файлы.

## Архитектура в проекте

- Новый blueprint, напр. `app/integrations/social/` (`telegram.py`, `vk.py`, `instagram.py`, `routes.py`, `secrets.py` или переиспользование `app/ai/secrets.py`).
- Роуты: `GET/POST /api/social/<provider>/status`, `/auth/start`, `/auth/token`, `/disconnect`; `POST /api/social/<provider>/publish` (ids работ + target).
- Персоны: новый модуль (напр. `app/personas/`) + `personas.html`; роуты `/api/personas` (CRUD), `/api/personas/<id>/assets`, `/api/personas/<id>/publications`.
- AI-постмейкер: операция `social_post` в существующем реестре операций; роут `POST /api/ai/social-post` (по образцу `/api/ai/enhance`), результат — черновик в `ai_jobs`.
- UI: карточки авторизации в настройках (образец — CLI-интеграции), кнопка экспорта в `#selection-toolbar` медиатеки (Select Mode уже есть в `library.html`), модалка публикации с выбором соцсети/таргета/персоны и кнопкой «Сочинить текст ИИ».
- Секреты: только через keyring (`SystemSecretStore`, service `comfyui-meta-viewer`, username `social:<provider>`); конфиг — только несекретные поля (api_id, api_hash, app_id, scope).

## Что проверить на практике (не открытые вопросы)

Все вопросы плана решены; ниже — пункты, которые закрываются только живой проверкой на этапах реализации. Если проверка выявит расхождение с планом, вносим корректировки.

- **Telegram (этапы 2–4).** MTProto-вход на реальном аккаунте (QR или phone+code), сохранение и повторное использование сессии через keyring, отправка в целевые таргеты (контакт / Saved Messages / группа, в т.ч. album).
- **VK (этап 5) — блокер подтверждён ресёрчем (2026-08, см. D-010).** Выдача scope `wall` новым приложениям прекращена. На практике проверяем, что реально доступно пользователю: (а) старое Standalone-приложение со scope `wall` → поток `blank.html` + перехват токена (redirect_uri, отличный от дефолтного, ломает методы Standalone-приложения; при неудаче — fallback: ручной ввод токена из адресной строки становится основным путём); (б) только community-токен → публикация в свою группу (ожидаемо работает — официальный путь). Валидация: `users.get` / `groups.getById` + пробный `wall.get`.
- **Instagram (этап 6).** Стабильность Private API-сессии (instagrapi) при переиспользовании без повторных логинов. Риск блокировки низкий при соблюдении лимитов и единого профиля клиента (см. «Не обходим лимиты провайдеров»).
- **AI-постмейкер (этап 8).** Качество vision на слабых профилях: прямая картинка для мультимодальных vs `SceneSpec` (reconstruct) для остальных. Критерии приёмки: стабильность образа (5 генераций с одним `appearance`), снижение галлюцинаций (пост с ролью vs без на одном SceneSpec), попадание в стиль персонажа.

## Порядок реализации

Текущее состояние каждого этапа — в **чеклисте** (первый незаполненный `- [ ]` пункт = точка продолжения); спорные решения — в **реестре решений**.

1. Добавить `telethon` в зависимости; модуль `app/integrations/social/` с резолвером секретов (keyring).
2. Backend-флоу авторизации: start (QR/phone+code) → сохранение зашифрованной сессии → `status`.
3. UI-карточка «Telegram»: кнопка «Авторизоваться» (QR в модалке/инлайн), индикатор «Подключено: @user».
4. Экспорт: выбор работ → target (контакт / Избранное / группа) → publish.
5. (Потом) VK: публикация в свою группу community-токеном (основной путь); личная стена — только при наличии приложения со scope `wall` (D-010).
6. (Потом) Instagram по той же схеме (Private API).
7. Персоны: таблицы `personas` / `persona_assets`, страница `personas.html`, фильтр в библиотеке.
8. AI-постмейкер: операция `social_post`, роут `/api/ai/social-post`, модалка публикации (выбор персоны + «Сочинить текст ИИ»).
9. Линковка в редакторе (`workflow_editor.html`): поле «Персона» + авто-альбом персонажа.

Этапы 1–6 (транспорт) и 7–9 (персоны + AI) независимы и могут идти параллельно: AI-слой не зависит от конкретной соцсети, а транспорт не зависит от персон.
