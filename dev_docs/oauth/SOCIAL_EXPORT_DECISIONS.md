# Реестр решений: социальный экспорт (в обход / в развитие плана)

Зачем этот документ: фиксируем обоснования решений, которые пришлось принять в обход или в развитие текущего плана, — чтобы человек и будущие ИИ-агенты понимали, почему сделано так, а не иначе, и могли **пересмотреть** решение при появлении лучших вариантов.

## Как пользоваться (для человека и ИИ-агентов)

- Новая запись добавляется при каждом спорном/неожиданном решении во время практической части (или при развитии планирования).
- Формат записи — краткий ADR:
  - **Контекст** — что заставило принимать решение, ограничения.
  - **Решение** — что сделали.
  - **Почему** — обоснование (факты, ссылки, рассуждение).
  - **Альтернативы** — что рассматривали и почему отбросили.
  - **Статус** — `proposed` / `accepted` / `superseded` / `rejected` + дата.
- Пересмотр решения: старую запись помечаем `superseded` (со ссылкой на новую) или дописываем «Пересмотрено» с новой датой; старый текст не удаляем — история важна.
- Связанные пункты чеклиста указываем в графе «Связано» (план/чеклист).

## Записи

### D-001 — Telegram/Instagram: только ручная публикация
- **Контекст:** автоматизация от личного аккаунта часто воспринимается как риск бана.
- **Решение:** публикация только по явной кнопке пользователя; один publish = один клик; без шедулинга, батчей, авто-повторов и массовых рассылок. Зафиксировано как жёсткий constraint в плане («Общие принципы»).
- **Почему:** сам по себе факт публикации через API аккаунт не блокирует — иначе сервисы не давали бы API вовсе и прекратили поддержку интеграций. Защита обеспечивается **rate limits**, которые сервисы уже встроили; бан возможен только при попытке **обойти** аккаунтные лимиты (массовость, обход лимитов, смена идентичности). Ручной режим — это UX-контракт «не обходим лимиты», а не снижение частоты: он делает массовость/обход физически невозможными. Плюс низкий объём = низкая нагрузка на аккаунт.
- **Альтернативы:** авто-публикация по расписанию/событиям — отклонено (риск обхода лимитов, нарушение UX-контракта).
- **Статус:** accepted (2026-08).

### D-002 — VK: личные сообщения недоступны
- **Контекст:** изначально Цель 2 включала и отправку в личку.
- **Решение:** право `messages` новым приложениям через Implicit Flow **не выдаётся** (dev.vk.com) → `messages.send` недоступен. Остаётся публикация только на стену (своя и группы, где пользователь администратор, `from_group=1`).
- **Почему:** ограничение платформы, обойти штатно нельзя; для целей продукта (публикация работ) стена достаточна.
- **Альтернативы:** старые приложения с уже выданным `messages` (недоступно новым); API-ключи пользователя (не подходит для автоматизированной публикации). 
- **Статус:** accepted (2026-08). Проверка фактической выдачи scope `wall` — пункт практической проверки (чеклист, этап 5).

### D-003 — Telegram: MTProto/Telethon вместо Bot API
- **Контекст:** нужно публиковать от имени личного аккаунта, а не бота.
- **Решение:** MTProto-клиент **Telethon 1.44.0** (совместим с Python 3.12, венв 3.12.5); авторизация QR или phone+code; сессия в keyring.
- **Почему:** Bot API действует только от имени бота; сессия tdata Telegram Desktop не читается сторонними библиотеками (зашифрована и привязана к сборке).
- **Альтернативы:** Bot API — отклонено (не та сущность); чтение tdata — невозможно; Telegram Login SDK (OIDC) — см. D-008.
- **Статус:** accepted (2026-08).

### D-004 — Instagram: Private API (instagrapi) вместо Graph API
- **Контекст:** нужно публиковать фото/видео/карусели от личного аккаунта, полностью локально.
- **Решение:** **instagrapi 2.18.12** (требует Python ≥3.8 — на 3.12 ок); сессия `dump_settings()` в keyring.
- **Почему:** Graph API публикует только в Business/Creator-аккаунты, требует Facebook Page + app review + короткоживущие токены — несовместимо с «личный аккаунт, локально, без деплоя».
- **Альтернативы:** Graph API — отклонено; ручной постинг — не цель.
- **Статус:** accepted (2026-08). Риск checkpoint/блока не является «баном за сам факт»: сервисы ограничивают rate limits, а не наличие интеграций; блокировка наступает при обходе аккаунтных лимитов или аномальном поведении (смена IP/UA, массовость). Митигация: соблюдаем лимиты и единый профиль клиента (один клиент/один IP/один UA).

### D-005 — Секреты только в keyring (Windows Credential Manager / DPAPI)
- **Контекст:** требование «другой локальный пользователь Windows не должен вытащить секреты из файлов приложения».
- **Решение:** все секреты (`social:telegram`, `social:vk`, `social:instagram`, Telegram StringSession, VK/Instagram токены) — через `keyring` (`SystemSecretStore`, service `comfyui-meta-viewer`); в ConfigStore и UI — только несекретные поля (`api_id`, `api_hash`, `client_id`, `scope`).
- **Почему:** keyring на Windows использует DPAPI/Windows Credential Manager — секрет читается только тем же Windows-пользователем; не попадает в репозиторий/конфиги-json. Бэкенд подтверждён: `keyring.backends.Windows.WinVaultKeyring`.
- **Альтернативы:** файл сессии с паролем / каталог с ограниченными правами — резервный вариант, менее прозрачен.
- **Статус:** accepted (2026-08).

### D-006 — Персона: legend / appearance / examples — независимые поля
- **Контекст:** неясно, как «биография» персоны должна влиять на генерацию изображений vs текстов постов.
- **Решение:** три независимых поля с разными точками инжекции: **legend** → роль агента (системная инструкция) для `social_post`; **appearance** → стабильный identity-блок только для генерации изображений; **examples** → few-shot стиля для текстов. Персона — слой в InstructionBundle (компилятор 06A), не отдельный агент.
- **Почему:** разделение предотвращает влияние биографии на внешность (галлюцинации облика) и наоборот; композиция «технический скилл + биография поверх» снижает галлюцинации текста.
- **Альтернативы:** единое «описание персоны» — отклонено (смешение ролей полей).
- **Статус:** accepted (2026-08). Критерии приёмки — в чеклисте, этап 8.

### D-007 — AI-постмейкер: vision (картинка vs SceneSpec) + хештеги
- **Контекст:** модель должна «видеть» выбранные работы, но не все профили мультимодальны.
- **Решение:** для мультимодальных профилей изображение передаётся напрямую; для остальных — структурированное описание (`SceneSpec` из операции `reconstruct`). Жёсткий запрет выдумок в манифесте `social_post`. Хештеги — «персона + контент», до N (Instagram ~10, VK 3–5, Telegram 0), всё редактируемо.
- **Почему:** универсальный путь через text-only описания теряет визуальные детали; прямой путь на слабых моделях недоступен. Хештеги «персона + контент» связывают персону с темой поста и остаются под контролем пользователя.
- **Альтернативы:** всегда SceneSpec — проще, но слабее на мультимодальных профилях; хештеги только из темы — теряется связь с персоной.
- **Статус:** accepted (2026-08). Качество vision на слабых профилях — пункт практической проверки (чеклист, этап 8).

### D-008 — Telegram Login SDK (OIDC) отклонён
- **Контекст:** рассматривался официальный «Log In With Telegram» (SDK, OIDC, анонс марта 2026) как возможная альтернатива MTProto.
- **Решение:** отклонено.
- **Почему:** это механизм identity/логина, а не публикации: SDK не позволяет приложению публиковать медиа как пользователь; требует бота + предварительно зарегистрированные публичные web-URL — нарушает ограничение «полностью локально, без деплоя».
- **Альтернативы:** MTProto/Telethon (принято, D-003).
- **Статус:** rejected (2026-08). Если появятся новые возможности публикации от личного аккаунта через официальный SDK — пересмотреть.

### D-009 — VK: перехват токена через redirect_uri `blank.html`
- **Контекст:** для получения user-токена без деплоя используется Implicit Flow с `redirect_uri=https://oauth.vk.com/blank.html`; токен приходит в URL-фрагменте.
- **Решение (провизорное):** перехват `access_token` из фрагмента через локальный слушатель / helper-страницу; fallback — копирование токена из адресной строки.
- **Почему:** нет webhook/хостинга; Implicit Flow — единственный путь без серверной части.
- **Важно:** redirect_uri, отличный от дефолтного, ломает доступ к методам Standalone-приложения — это **потенциальный блокер VK-транспорта целиком**, а не рядовой пункт проверки. Проверяется на этапе 5. Если перехват окажется нереализуем — fallback (ручной ввод токена из адресной строки / десктопный клиент) становится **основным путём** авторизации VK; планировать интерфейс так, чтобы оба пути существовали с самого начала.
- **Пересмотрено (2026-08, ресёрч):** для **старых** Standalone-приложений `blank.html` остаётся рабочим redirect_uri (нестандартный — `invalid_scope`), но **новые** приложения через VK ID scope не получают вовсе — значит `blank.html`-поток актуален только для старых приложений/генераторов токенов. Основной путь VK-транспорта — community-токен на свою группу (см. D-010).
- **Статус:** provisional (2026-08) — закроется практической проверкой; при появлении данных от ресёрч-агентов уточнить.

### D-010 — VK: user-токен личной стены для новых приложений недоступен; основной путь — community-токен
- **Контекст:** план предполагал user-токен (`photos,video,wall,offline`) + `wall.post` на личную стену.
- **Решение:** VK-транспорт строится вокруг **community-токена → публикация в свою группу** (`owner_id=-<gid>`, `from_group=1`) как основного пути. Личная стена — только если у пользователя есть старое приложение (до ~марта 2025) с выданным scope `wall`, либо через документированный workaround (генератор токенов `vkhost.github.io` — неофициальный, токены привязаны к IP); для продукта это не дефолт.
- **Почему:** ресёрч (2026-08): (1) dev.vk.com — wall/photos/video для user-токенов «выдаётся в исключительных случаях через запрос в поддержку»; поддержка (фев–мар 2026) систематически отказывает по оферте п.7.2; (2) легаси Implicit Flow деприкейтнут для новых приложений → VK ID (`id.vk.com`) OAuth2+PKCE не выдаёт scopes API-методов; (3) community-токен — официально поддерживаемый путь для стен сообществ, особых прав не требует.
- **Альтернативы:** запрос прав через поддержку (шанс ≈0); `vkhost.github.io` (не для продукта); VK ID scopes (не дают API-прав).
- **Статус:** accepted (2026-08). Практическая проверка — чеклист, этап 5.
